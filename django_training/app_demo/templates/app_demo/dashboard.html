Django Architecture Playbook

A side-by-side comparison of Traditional Django (Fat Views / Generic CBVs) vs. Layered Architecture (Repository-Service-View).

Path A: Traditional Django

Standard Generic CBVs & Fat Views

Utilizes standard Django workflow where Class-Based Views perform direct database queries via the model ORM, handle form validation and model saves inside view methods (`form_valid()`), and coordinate error boundaries at the HTTP layer.

  • ✗ Fat Views: Business logic, model saves, and authorization coupled to HTTP.
  • ✗ ORM Coupling: Views must know database structure, filters, and fields.
  • ✓ Simplicity: Fast setup, excellent for simple CRUD & MVPs.

Path B: Layered Architecture

Repository - Service - Thin View Pattern

Isolates concerns across three distinct layers. Views remain thin, calling a Service which orchestrates logic and transactions. The Service queries DB records exclusively through a Repository, handling errors gracefully via Go-style return tuples.

  • ✓ Thin Views: HTTP routing and form rendering only. No model access.
  • ✓ Go-style tuples: Catch exceptions in services and return `(result, error)`.
  • ✓ Repository CRUD: Database queries and mutations fully isolated.

Architectural Layer Comparison

How each concern is handled side-by-side

Concept Path A (Traditional) Path B (Layered)
Data Access (ORM) Direct queries inside Views (e.g. `Course.objects.filter(...)`). Isolated in `CourseRepository`. Views call `CourseService`.
Business Logic Mixed inside Views, Forms, or saved inside Model methods. Encapsulated in `CourseService` methods.
Error Handling Exceptions bubbled up to HTTP and caught by standard Django middleware. Caught inside `Service`, returning Go-style tuples: `(result, error_msg)`.
Transaction Boundary Database atomic transactions tied to HTTP requests (all-or-nothing). Fine-grained transactions controlled programmatically in `Service`.
Audit Fields injection Injected manually in view (`form.instance.created_by = request.user`). Bound dynamically using `PermissionServiceMixin` and `CourseRepository(user)`.
Testability Requires mocking HTTP requests and complete DB setup. Repository and Service layers can be unit-tested without HTTP contexts.
